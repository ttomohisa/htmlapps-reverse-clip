## Implemented candidate safeguards

| Setting | Compact | Standard / 720p-class | High / 1080p-class |
| --- | --- | --- | --- |
| Long edge max | 360px or 720px | 1280px | 1920px |
| Short edge max | Same as long edge | 720px | 1080px |
| Range | 0.5–10s | 0.5–10s | 0.5–5s |
| Output FPS | 15 (experimental) | 15 (experimental) | 15 (experimental) |
| Maximum YUV420 frame cache **estimate per chunk** | 48 MiB | 48 MiB | 48 MiB |
| 16:9 typical frames per chunk | up to 30 | 30 (~39.6 MiB) | 16 (~47.5 MiB) |
| Reverse chunks / Ping-pong chunks | at most 8 / 16 | at most 8 / 16 | at most 8 / 16 |

- The displayed quantity is a **lower-bound estimate of buffered YUV420 frames**, not process peak memory or a strict device RAM cap. Decoder, filter graph, encoder, JS, WASM heaps and browser overhead are additional. Builder's separate 96 MiB per-chunk estimate guard still applies.
- The existing Builder runner verifies per-chunk frame counts and the remux verifies a complete frame count, including 2N–2 Ping-pong output. Both presets retain aspect ratio, cap short and long edges, and never upscale. The app does not silently truncate a selected range or lower requested quality.
- Optional audio-track inspection has its own WASM instance. It is now aborted/disposed when an export starts, and may resume after the video job finishes. The audio setting remains **No audio** by default.
- Simultaneous Create calls are rejected, failed video preview clears its object URL/element and navigation/pagehide returns to the empty state so bfcache cannot revive a revoked preview.
- Both ST and MT still pin experimental Builder Actions artifact `11794061552` (expires **2026-10-20**), not an immutable corresponding-source GPL release.

The existing Android photo/cloud provider workaround **intentionally reads and copies files up to 64 MiB** into memory before preview and processing, because some providers cannot be read in a Worker. ### Browser memory measurement method caveat

The original desktop ST and new MT figures sum per-process RSS, which
can count shared memory more than once. MT results from GitHub Actions
must **not** be compared directly against ST results from the execution
container or presented as device RAM consumption. A later on-demand test
can capture sampled process-tree PSS/USS on Linux (more informative than
RSS, but still not a mobile-device measurement). Do not conclude that
MT uses several GiB of unique physical memory from summed RSS alone.

## 2026-10-14 — Experimental Android input-copy avoidance (NOT hardware accepted)

An Android photo/file picker may expose an original `File` that plays
in `<video>` but fails in FFmpeg WORKERFS `FileReaderSync`. Previous
builds eagerly copied the **entire original file** when it was at most
64 MiB, before allowing the first preview. That preserved earlier
phone compatibility but incurred an avoidable allocation for ordinary
local files.

The v0.6.0 candidate now performs a **bounded Worker probe** first:
it reads only the first and last 32 bytes via `FileReaderSync`
inside a disposable Blob Worker. If both reads succeed, the app keeps
the original File/WORKERFS route and does **not** call the whole-file
`File.arrayBuffer()` at selection. If the Worker probe fails,
is unsupported, or exceeds 2.5 seconds, the existing <=64MiB
local in-memory detached-Blob/MEMFS fallback is still used.
The existing conversion-time WORKERFS read-error retry remains.
A cancelled/replaced/timed-out source aborts and terminates the probe,
releases its Blob URL, and cannot revive stale input.

**This does not prove WorkerFS will remain readable after source preview.**
Some Android photo providers revoke worker access later, when the
conversion begins; that case may still require the <=64MiB fallback
or fail if permissions have expired. It also does **not satisfy the
strict G2 rule prohibiting whole-source memory copies up to 1 GiB**:
memory fallback still copies files <=64MiB. No OPFS, IndexedDB,
Service Worker Cache or remote staging has been introduced.
This is an allocation reduction for **eligible** files, not
a universal copy-free guarantee or physical Android acceptance.
