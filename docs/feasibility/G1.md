## Why the gate stays closed

Native FFmpeg command-line success validates **algorithm shape only**, not the Browser Kitty profile's public-libav API, low-memory implementation, browser Worker/CSP, real mobile performance, audio, orientation, or Safari's MP4 save behavior.

`htmlapps-ffmpeg-wasm-builder` currently has no `video-reverse` profile or enabled `reverse`/`areverse` filters for the speed and graph profiles (checked 2026-10-11). Building the runtime is a separate step **after feasibility has sufficient evidence**; do not pass G1 without an actual WASM MP4 test and mobile hardware.

## Memory risk and explicit test points

`reverse` buffers frames; FFmpeg's documentation recommends trimming first. Approximate YUV420p frame storage: 720p 30fps 10s ≈ 395 MiB, 1080p 30fps 5s ≈ 445 MiB, **before** codecs, duplicated decode buffers, audio, WASM heaps and browser overhead. Pre-scaling before reversing reduces storage, but input decoding remains costly.

Investigate 1–2s chunk reversal in reverse chunk order with frame timestamp proof and no boundary loss. Mobile Safari page termination or continuous long-running work is a hard stop rather than a reason to silently lower quality.

## Native memory experiment (2026-10-11)

Linux x86_64, FFmpeg **7.1.5**, Node **22.16.0**; inputs generated with `testsrc2`, H.264/yuv420p, 30 fps; output H.264/libx264 `-preset ultrafast -crf 32`, no audio. Peak RSS from `/usr/bin/time -f '%M'`. These figures are **not** WASM heap measurements or phone results.

| Case | Output frames | Peak RSS | Elapsed wall time |
|---|---:|---:|---:|
| 720p / 10 s whole reverse | 300 | 531,536 KiB ≈ 519 MiB | 0.52 s |
| 720p / 10 s in five separate 2-s reverse jobs | 300 total after concat | maximum 201,344 KiB ≈ 197 MiB per job | 0.16–0.25 s/job + 0.07 s concat |
| 1080p / 5 s whole reverse | 150 | 652,280 KiB ≈ 637 MiB | 0.55 s |

Native segmentation wrote five independent MP4 pieces and concatenated them **in reverse order** using the concat demuxer and stream copy. The total decoded frame count was 300 in both variants; their measured durations differed slightly (9.966667s vs 10.000000s), so output timestamp boundaries still require deeper WASM-level checking.

**Implication:** bounded chunks plausibly reduce peak memory. The lower peak **does not prove** correctness under VFR, rotated MOV, audio, mobile Safari, or FFmpeg WASM. In particular, chunk outputs must have consistent time bases, codec parameters, leading frame policy, and timestamps before copy concatenation can be selected for production.

## Android FileReaderSync/WORKERFS failure report (2026-10-11)

After the v0.1.1 Preview was tested by the user on Android, MP4 export failed **before input decode/processing**. The supplied UI error was:

```text
Failed to execute 'readAsArrayBuffer' on 'FileReaderSync': The requested file could not be read, typically due to permission problems that have occurred after a reference to a file was acquired.
Recent FFmpeg log:
[stderr] ffmpeg-filter-builder-runner 0.3.0 / FFmpeg bf1b838 / threading=single-thread
[stderr] time-range start=0.000s duration=1.000s
```

**Observed:** the runner initializes and receives a 0–1s range, but a WORKERFS synchronous read of the original picked `File` fails. This is **not proof of invalid codec, decoding failure or insufficient compute performance**. The exact underlying Android photo/file provider and OS version are not known. Device/media content and filename are not logged.

**Mitigation in v0.1.2 (unverified on Android):** For mobile files <=64 MiB, initiate `File.arrayBuffer()` immediately after selection and create a new local Blob. Supply that Blob to MEMFS rather than passing the Android provider `File` to WORKERFS. This bypasses Worker-side FileReaderSync for the copied input; if main-thread source access is also denied, show an actionable save-locally/reselect message. For desktop WORKERFS and oversized mobile files, retain the zero-copy path and retry once via MEMFS on this specific read failure if file size is within 64 MiB. The copy increases peak memory and is **not a solution for arbitrary 1GiB inputs**. Protect source replacement/cancellation by generation tokens and clear copied buffers when the source changes.

**Verification required:** actual reporting Android device: same MP4, 0–1s, 360p, WASM convert/playback/download; record `reverseConversion.inputTransport` and elapsed time. Also test selection from local storage vs Google Photos/cloud provider, 64MiB+ behavior, iPhone Safari and 2 consecutive runs. **Gate G1 remains INVESTIGATE / NOT GO** until mobile export, frame order and performance are proven.

## v0.1.2 Android file-reader mitigation regression (2026-10-11)

**Trigger:** The user's actual Android Preview error was `FileReaderSync.readAsArrayBuffer` / `NotReadableError` before media decode. The code now avoids presenting the original picker-backed `File` to Emscripten WORKERFS on supported small mobile inputs: it reads the file immediately via asynchronous `File.arrayBuffer()`, creates an in-memory Blob, previews that Blob, and uses FFmpeg MEMFS rather than Worker-side `FileReaderSync`. This requires extra memory and is deliberately limited to **64 MiB input size**. Large input stays on WORKERFS; only a matching read failure triggers a bounded fallback. No data is uploaded.

**Windows template CI / Preview:** build [run 38127347429](https://github.com/ttomohisa/htmlapps-reverse-clip/actions/runs/38127347429) passed for the final application fix, producing both readable and self-extract HTML. The latest source also retains `'wasm-unsafe-eval'` and `connect-src 'none'`.

## 5-second real-WASM chunk join milestone (2026-10-11)

Builder commit `47448852` ([dedicated build and Chrome smoke](https://github.com/ttomohisa/htmlapps-ffmpeg-wasm-builder/actions/runs/38129319876)) adds experimental `--concat` using public libavformat. It remuxes ordered, separately reversed, video-only H.264 chunks, checks consistent codec parameters and monotonic DTS, and refuses incomplete metadata. It does not support audio/pingpong. The original 0.1–2-second reverse runner and the Android MEMFS fallback are retained.

**Independent frame-order proof (actual WASM, not just simulation):** A 160×90, 10fps, 5-second marker video was divided into source windows 0–2, 2–4, 4–5 seconds, reversed individually in Chromium, then remuxed in the order [4–5,2–4,0–2]. Native `ffprobe` and `ffmpeg` re-decoded the final MP4 and confirmed **exactly 50 frames, 5.000 seconds, descending color markers from first to last with no chunk-boundary inversion**. SHA-256 of that test MP4: `7e985fd07aa554f1afc8deed85a5544ae4e634343a25c6be83ddaf4acf7776ed`.

**Application v0.1.3 experiment:** the planned selection is 0.5–5 seconds, output at 15fps, rounded to nearest output-frame boundary (UI discloses up to ~0.033s shift). Balanced 1–3 chunks, each at most 2 seconds, are executed in reverse chronological order then remuxed. Quality labels now accurately specify **long edge 360px/720px**, not full 720p resolution. G1 remains **INVESTIGATE**: Android and iPhone real-device 5s processing, VFR/HEVC orientation, long-run memory, `file://` and source-complete permanent Builder release all remain unverified.
