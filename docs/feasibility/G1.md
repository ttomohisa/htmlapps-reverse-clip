## Why the gate stays closed

Native FFmpeg command-line success validates **algorithm shape only**, not the Browser Kitty profile's public-libav API, low-memory implementation, browser Worker/CSP, real mobile performance, audio, orientation, or Safari's MP4 save behavior.

`htmlapps-ffmpeg-wasm-builder` currently has no `video-reverse` profile or enabled `reverse`/`areverse` filters for the speed and graph profiles (checked 2026-10-11). Building the runtime is a separate step **after feasibility has sufficient evidence**; do not pass G1 without an actual WASM MP4 test and mobile hardware.

## Memory risk and explicit test points

`reverse` buffers frames; FFmpeg's documentation recommends trimming first. Approximate YUV420p frame storage: 720p 30fps 10s ≈ 395 MiB, 1080p 30fps 5s ≈ 445 MiB, **before** codecs, duplicated decode buffers, audio, WASM heaps and browser overhead. Pre-scaling before reversing reduces storage, but input decoding remains costly.

Investigate 1–2s chunk reversal in reverse chunk order with frame timestamp proof and no boundary loss. Mobile Safari page termination or continuous long-running work is a hard stop rather than a reason to silently lower quality.

## Native memory experiment (2026-10-11)

Linux x86_64, FFmpeg **7.1.5**, Node **22.16.0**; inputs generated with `testsrc2`, H.264/yuv420p, 30 fps; output H.264/libx264 `-preset ultrafast -crf 32`, no audio. Peak RSS from `/usr/bin/time -f '%M'`. These figures are **not** WASM heap measurements or phone results.

| Case | Output frames | Peak RSS | Elapsed wall time |
|---|---:|---:|---:|
| 720p / 10 s whole reverse | 300 | 531,536 KiB ≈ 519 MiB | 0.52 s |
| 720p / 10 s in five separate 2-s reverse jobs | 300 total after concat | maximum 201,344 KiB ≈ 197 MiB per job | 0.16–0.25 s/job + 0.07 s concat |
| 1080p / 5 s whole reverse | 150 | 652,280 KiB ≈ 637 MiB | 0.55 s |

Native segmentation wrote five independent MP4 pieces and concatenated them **in reverse order** using the concat demuxer and stream copy. The total decoded frame count was 300 in both variants; their measured durations differed slightly (9.966667s vs 10.000000s), so output timestamp boundaries still require deeper WASM-level checking.

**Implication:** bounded chunks plausibly reduce peak memory. The lower peak **does not prove** correctness under VFR, rotated MOV, audio, mobile Safari, or FFmpeg WASM. In particular, chunk outputs must have consistent time bases, codec parameters, leading frame policy, and timestamps before copy concatenation can be selected for production.

## Chromium browser diagnostic validation (not G1 mobile acceptance)

The build generated by template-based GitHub Actions (commit `0d4950e`) passed repository checks and produced readable and self-extract HTML. An offline-capable Chromium 144 automation session on Linux loaded the built HTML through `about:blank` / `page.set_content` because the test environment's URL navigation policy blocks both `file://` and `127.0.0.1` navigation. **This does not count as testing `file://` or a hosted URL.**

- Loaded a synthetic 720p 10-second H.264 MP4 through file selection; metadata displayed duration/dimensions; source kept in browser memory.
- Reported the 5-second selection's approximate YUV420p frame lower bound (~198 MiB).
- Passed Blob Worker echo, video seek to 0.2s (~13ms on this test run), manual JSON download with media properties but no video filename, and JA-to-EN switching.
- Discovered initial template CSP blocked the minimal WebAssembly module. **Fix:** explicitly allow `'wasm-unsafe-eval'` in the app CSP (not `'unsafe-eval'`). With this change, the empty WASM module and Blob Worker passed in the Chromium `about:blank` test; dedicated FFmpeg WASM still has not been tested.
- Detected horizontal overflow at mobile width due to diagnostic filename + download button; fixed with stacked controls on narrow viewports.
- The self-extracting build still requires re-verification after this CSP change; do not mark `file://` or phone validation passed.

## Self-extract wrapper CSP regression (2026-10-11)

Browser smoke on CI-built commit `aef258d` showed the readable `dist/index.html` supports the minimal empty WASM module, Blob Worker and video-seek diagnostic, but the `dist/index.self-extract.html` wrapper kept the upstream template's old CSP lacking `'wasm-unsafe-eval'`. The wrapper's policy remains active after `document.open/write/close`, so the restored app could not compile even an empty WASM module. The Reverse Clip wrapper generator now explicitly permits only `'wasm-unsafe-eval'` (not `'unsafe-eval'`) and retains `connect-src 'none'` and all other restrictions. Retest **both** variants after the CI rebuild; this regression does not qualify as mobile G1 evidence.
